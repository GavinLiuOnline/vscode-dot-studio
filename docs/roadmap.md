# Roadmap

Ordered by what is needed to drop Visual Studio for daily work. Phases 1–21 are done (see [History](history.md)): web apps, SOAP clients, templates, tests, private feeds, the Visual Studio basics, publishing, readiness for others, solutions, projects and configurations, code cleanup and refactoring, and the second rounds for run & debug, for the Solution Explorer, for NuGet and for connected services. Phase 22 is quality and documentation, phase 23 the small limitations left until after the code review, phase 30 what may come later, phase 35 packages per target framework (last, only if it proves necessary), phase 40 the issues with the Open VSX C# extension (the case for bundling our own server, not planned), phase 45 refactorings inside the C# server, phase 50 navigation and debugging extras. Everything else is under Not Planned: a change request on GitHub brings it back.

What still needs a check in VS Code itself is listed in [manual-testing.md](manual-testing.md).

## Phase 35: Per-framework packages
**Goal** (hard and error prone: the team hand-writes these project files for a reason, so this comes last and only if it proves necessary; the read-only display of each framework's packages is the safe part, editing around conditions the risky one): Projects that reference different packages per target framework (`net10.0` and `net8.0` in one `.csproj`, or conditions in `Directory.Build.props` and `Directory.Packages.props`), which the team writes by hand because Visual Studio's UI cannot express them, are shown and edited correctly instead of only for the first framework. To start with real examples of what the team writes.

- Design basis (from another NuGet manager's multi-targeting): each target framework is its own row with its own current version, picker and update target computed within its own major line (the `net9.0` row proposes 9.x although 10.x exists; crossing a line asks first and names it), a framework without the package gets a row offering to add it there alone, and one unconditional reference that should move for a single framework is an explicit split into one conditional group per framework with the others left where they were. Plain `dotnet add package` without `--framework` rewrites every conditional group to one version, which is why the edits have to be ours
- [ ] Evaluate multi-targeted projects per target framework (today only the first one is evaluated) and show each framework's packages in the tree, the NuGet manager and the update confirmation
- [ ] Edits respect conditions: update the `PackageVersion` or `PackageReference` that applies to the framework (or all of them, after a confirmation naming them) instead of the first match; a new conditional entry can be written for a chosen framework
- [ ] Packages declared in an imported props file without Central Package Management (`Directory.Build.props` with a `PackageReference`, e.g. one analyzer for every project): update and remove edit that file after a confirmation naming the projects it reaches (the `dotnet` CLI refuses: "Cannot edit items in imported files"); seen with `Cirrus.RuleSet` in the test projects of Cirrus.Core, where Update Selected now fails for each of them with that message, also offering "Set for This Project Only"; the machinery for `Directory.Packages.props` exists
- [ ] Consolidate and Updates ignore version differences that are on purpose between target frameworks or projects (e.g. `NeinLinq` 2.2.1 for `net471` and 7.4.0 for `net10.0`)
- [ ] Never offer an orphan removal of a version that another framework still uses (today any multi-targeted project suppresses the prompt)
- [ ] Docs, GIF and manual-testing entries for the conditional cases

## Phase 40: Our own C# language server and debugger (0.6)
Parked (2026-11-02): maintaining our own client and server is more than we want to carry; this list stays as the record of what the Open VSX extension costs us, and as the case if a Phase 45 style extension is not enough.

The extension needs a C# extension for the language server and the debugger (`coreclr`). The one from Open VSX (`muhammad-sammy.csharp`, the Roslyn language server with netcoredbg) has limits we run into; they are the reasons to bundle our own (the Phase 30 item "No C# extension needed" has the how). Found so far (2026-11), with what was checked:

- **Debugger is netcoredbg, not Microsoft's:** a project started with "Start without debugging" (`noDebug: true`) is attached to the debugger anyway and gets no breakpoints (see Known bugs); no Hot Reload with the debugger attached and no Edit and Continue (`dotnet watch` refuses assembly updates while a debugger is attached); it cannot attach to Mono or .NET Framework processes (only `coreclr`).
- **The language context of a multi-targeted file can only be switched by its command:** the context (project and target framework a file is analysed in: `#if` regions, diagnostics, IntelliSense) is kept per file in memory and starts on the first framework. The only way in is the undocumented command `csharp.changeProjectContext(document, { projectName, tfm })` (read from `dist/extension.js` of 2.160.9; matches the label `Project (tfm)`), there is no way to read the current context, to set it for a project or to have it persist. Select Framework drives it for the open files and for each file as its editor comes to the front.
- **Its own context switch and ours do not know of each other:** choosing a context in the C# extension's status item or with *Change Project Context* does not update our Select Framework dropdown (the extension only fires an event for itself, nothing we can subscribe to or read), and our dropdown can only push.
- **Menu entries we cannot remove:** the extension adds *Run Tests in Context* and *Debug Tests in Context* (`dotnet.test.runTestsInContext`, `dotnet.test.debugTestsInContext`) and *Change Project Context* to the editor's context menu, with fixed `when` clauses and no setting; they go through its own test runner, so *Debug Tests in Context* does nothing with our Test Explorer, while *Debug Test at Cursor* (VS Code's, through our controller) works. Only its test code lens has a setting (`dotnet.codeLens.enableTestsCodeLens`). Checked in its `package.json` (2.160.9).
- **A switched context does not always bring the preprocessor symbols along (reported, not investigated):** with the context on `net472`, `NET471_OR_GREATER` is not defined in the hover/greyed regions; going to `net471` and then `net472` defines it. It may be the language server's workspace state after a switch, or our call; to check with a language server we control.
- **The project load follows every project file edit:** each `dotnet add package` makes the server reload the project (and the projects that reference it), run `dotnet restore` and start a new build host process ("Completed (re)load of N project(s)" in its log, several seconds each, six in a row for one update); on a 50-project solution this is part of the load that froze a PC during a package update (cause not proven, see Phase 23).
- **Not ours to change:** release cadence and which Microsoft features the Open VSX build leaves out; a bug in the server is fixed there, not here.

## Phase 45: Refactorings inside the C# server
The C# extension's Roslyn server loads extra assemblies given with `--extension`. The C# extension collects them from two places (read in its `dist/extension.js`, 2.160.9): the `contributes.csharpExtensionLoadPaths` of every installed VS Code extension (an array of paths relative to that extension, so ours can ship one without touching anyone's settings), and its setting `dotnet.server.extensionPaths`. A small .NET assembly of ours, compiled against the Roslyn packages and shipping nothing of Roslyn, adds `CodeRefactoringProvider`s that appear in `Ctrl+.` next to the server's own, with its semantic model, in the server's process (net10.0 here), for projects of any target framework (the server reads source and reference metadata; `net4x` projects go through its `BuildHost-net472`).

**Spike done (2026-11-02):** a net10.0 library of 11 KB with one provider ("Extract interface IOrder (all public members)"), started by hand with `Microsoft.CodeAnalysis.LanguageServer --stdio --extension <dll>` on the Contoso sample and asked over LSP: the server loads it, `textDocument/codeAction` on a class name lists our action between its own, and `codeAction/resolve` gives the right edit. Not yet tried: through the C# extension in VS Code itself (the `contributes` route), and the Microsoft build. The spike compiled against the server's own `.roslyn/*.dll`; a release needs the public Roslyn packages of a version the server still binds (see the second item).

What the server offers already, by the same probe: at a class name *Extract interface...* (resolves without a dialog to an `interface` for all public members above the class and `: IName` on it, in the same file), *Extract base class...*, *Generate constructor*, *Add DebuggerDisplay*; at members *Encapsulate field*, *Generate Equals and GetHashCode*, *Wrap parameters*, *Add null check*, *Replace property with method*, *Introduce field*. Not offered in any of those places: Change Signature, Move to Namespace, Pull Members Up / Push Down (the last needs a type with a base). So the candidates are those, and what the existing ones lack (a member picker, a target file).

- [x] Spike: the server loads a provider from `--extension` and offers it (see above); Extract interface is not the gap, it exists
- [x] Through the C# extension (2026-11-03): `contributes.csharpExtensionLoadPaths` in our `package.json` points at `out/server-extension/Shinobi.Refactorings.dll`; VS Code in its own Xvfb display on the Contoso sample shows "Shinobi: Extract interface IOrder (all public members)" in `Ctrl+.` on a class. Still to try: Microsoft's C# extension
- [ ] Which Roslyn version to compile against and how far a provider built for one server version loads in the next (public APIs only; a test that loads the built assembly into the installed server over LSP, as the spike's script does, and asks for the code actions)
- [x] The way in (2026-11-03): the server's message handlers (`IExtensionDocumentMessageHandler`, activated with `server/_vs_activateExtension`, called with `textDocument/_vs_dipatchExtensionMessage`, both reachable through the C# extension's `exports.experimental.sendServerRequest` with a RequestType-shaped first argument, a plain string kills the server). The extension registers a code action provider, the handler answers with the type's members and later the edits, a form in the editor area (`RefactoringPanel`, `refactor-view`) asks the choices; Extract Interface with member picker, name and new file is built on it (docs/enhanced-refactorings.md); the compile-time interfaces come from the `Microsoft.CodeAnalysis.ExternalAccess.Extensions` package on the dotnet-tools feed (`server-extension/NuGet.config`)
- [x] Extract Members to Partial Class (2026-11-03): the shared pieces now exist as `TypeRefactoring` (code action, form, server request, edits, save, project refresh; configured by a spec per refactoring), `MembersForm` (name, targets, member list with kinds, theme-coloured preview) and `MemberInfo`; the server side is a pair of handlers per refactoring (`...InfoHandler` lists, `...Handler` builds the edits, same result shape)
- [ ] The next refactorings, in the order of cost (the user decided on 2026-11-03 that Phase 45 also covers Rider's refactorings, not only Visual Studio's): Extract Superclass with a member picker and "make abstract" per member (the server's *Extract base class...* takes no choices), Pull Members Up (class or interface target, dependency warning for members that use what stays, a clash is an error), Use Base Type Where Possible (a checkbox of the two extracts: `SymbolFinder` usages whose accessed members all exist on the new type), Push Members Down, Convert Abstract Class ↔ Interface, Extract Class; and the Visual Studio ones: Move Type to Namespace, Change Signature (a form with the parameter list). Each applies as one edit (one undo step) and is checked by compiling the result in a unit test; a refactoring that touches several files is validated by a fork of the solution (new compiler errors are shown, not applied silently)
- [x] Packaging: `npm run build` first builds `server-extension/Shinobi.Refactorings` into `out/server-extension` (11 KB, compiled against Roslyn 5.0.0, nothing of Roslyn shipped; the server's 5.12.0.0 satisfies it); `.vscodeignore` lets the dll into the `.vsix`; CI and the release already have the .NET SDK
- [ ] Docs, manual-testing entries, and the LSP test above in CI (the server comes with the C# extension, so the test skips where it is not installed)

## Phase 50: Navigation and debugging extras (after Phase 45)
Ideas from JetBrains' ReSharper extension for VS Code (the refactorings are Phase 45); only what is not already there.

- [ ] Go to external sources, first look at what the C# extension has: its Roslyn server already navigates into metadata-as-source, decompiled code and SourceLink or embedded sources, switched by `dotnet.navigation.navigateToDecompiledSources` and `dotnet.navigation.navigateToSourceLinkAndEmbeddedSources` (both on by default in the Open VSX build 2.160.9; its command `csharp.showDecompilationTerms` shows the decompiler's terms). Nothing to build for the navigation itself; the gap is the UX: say what you landed in (a SourceLink file, embedded source, decompiled, metadata signatures only), and make it reachable from the Solution Explorer: Go to Definition from the package and assembly nodes under Dependencies (an assembly's types, a package's assemblies), so a library can be browsed without a call site
- [ ] Debugger extras that matter day to day: inline variable values in the editor while stopped (the DAP gives the values; VS Code has an inline values feature for languages that provide it), dependent breakpoints (a breakpoint that is only armed after another one was hit), a better attach picker (we have one: see Attach to Process). Smart step into and set next statement need the engine to support them: netcoredbg has no smart step into and I do not know of set next statement there, so both depend on the netcoredbg-or-own-debugger question (Phase 40, parked); check netcoredbg's current feature list before promising either

## Not Planned
- Accessibility of the Solution Explorer and the other views (ARIA tree roles, keyboard multi-select, links that cannot be focused, colour-only markers): to be done when someone opens an issue (A3-9, A3-10)
- An expand that arrives while the tree is being rebuilt can show collapsed for a moment; it is remembered and the next rebuild opens it (A2-12)
- Central Package Management: the Updates tab does not offer updates of pinned transitive packages (`CentralPackageTransitivePinningEnabled`; they have a `PackageVersion` but no reference); update them in `Directory.Packages.props`
- gRPC references: the Connected Services node of a project without that folder becomes the folder once a WCF reference creates it, and shows collapsed that once
- A Test Explorer run builds each test project on its own, one after the other (Visual Studio builds the selection once); a failed build reports its first errors in the test message and the whole output is in the Test Results
- The NuGet manager takes the package sources and their credentials from the solution's folder (like Visual Studio's manager); a `NuGet.Config` in a project's own subfolder is used by restore and builds but not by the manager's Browse, Updates and package details
- ASP.NET (IIS Express) and old-style project files on .NET Framework 4.x: SDK-style `net4x` projects load, build, use the NuGet manager, run their tests and run and debug with Mono on Linux and macOS, see [Troubleshooting](troubleshooting.md#known-limitations)
- `packages.config` and old-style project files
- Code navigation features that the C# extension already provides (Go to Definition, Find References, symbol search)
- Diagnostic Tools / profiler UI (the `dotnet-trace`, `dotnet-counters` and `dotnet-gcdump` CLI tools cover it)
- A `.resx` resource editor
- Task List (`// TODO` comments)
- Visual Studio's Git integration (also git status in the Solution Explorer): VS Code's Source Control view and Explorer cover it
- The other publish targets of Visual Studio, with the `.pubxml` format it writes for each: Azure App Service (ZIP deploy through the Azure CLI), container registry (the SDK's container publish), FTP/FTPS, IIS Web Deploy (Windows only); folder publishing exists and profiles for the other targets are listed but publish from Visual Studio; to be built if someone opens an issue
- `dotnet-svcutil` limits, not ours to fix: updating a reference Visual Studio created changes the generator version in every type of `Reference.cs` (svcutil 8.0.0 instead of Visual Studio's 2.0.2), and it cannot read .NET Framework assembly references (`<Reference Include="System.ServiceModel" />`; remove them when porting before updating a reference)
- Exclude From Project and Include In Project on old-style (non-SDK) projects, and Exclude for linked files: SDK-style projects only
- Drag & drop from VS Code's Explorer or the file manager into the Solution Explorer: a webview gets no file paths from such drops
- Central Package Management props files imported through a property (`$(SomeDir)/x.props`) or a wildcard, or located outside the opened folder, are not watched live (only imports written with a literal path, `$(MSBuildThisFileDirectory)` or `GetPathOfFileAbove` are, and outside files are re-checked when the NuGet manager gets focus): VS Code's file watching cannot see them; edit, then change a project file or reopen the NuGet manager
- Configure Service Reference (Visual Studio's dialog on a service reference to change its address, namespace and type reuse): Update Service Reference regenerates from the stored address in `ConnectedService.json` (`ExtendedData.inputs`), which can be edited by hand, or the reference removed and added again; to be built if someone opens an issue
- Search in the Solution Explorer (Visual Studio's Ctrl+;): Ctrl+P and Sync with Active Document cover it; to be built if someone opens an issue for it
- The diagnostic rules of each analyzer under Dependencies > Analyzers: `.editorconfig` sets their severities
- OpenAPI clients (Visual Studio's "Add Connected Service > OpenAPI"): Microsoft deprecated `<OpenApiReference>` and `dotnet openapi` in .NET 10 and recommends the generators' own tools (NSwag, Kiota with its VS Code extension); to be built if someone opens an issue
- Refactorings the C# extension's Roslyn server does not offer (Change Signature, Move to namespace, Pull members up, Visual Studio's Extract Interface dialog): see Phase 45 for a way in through the server's extension assemblies; not before it proves out
- Solution filters (`.slnf`, load part of a big solution): to be built if someone opens an issue
- Scaffolding ("New Scaffolded Item": controllers with EF, Identity): to be built if someone opens an issue
- Docker / docker-compose launch profiles: not used by the team, and those who use them write them by hand; to be built if someone opens an issue
- Encrypted NuGet credentials (`Password` is Windows DPAPI): on Linux the Azure Artifacts Credential Provider covers restore and build, and the NuGet manager explains rejected tokens; to be built if someone opens an issue
- Remote debugging on devices over SSH (`pipeTransport` launch configurations): not a Visual Studio feature for .NET (Visual Studio only attaches to running processes over SSH)
- Code coverage in the Test Explorer: an IDE's coverage is slow or slows the IDE down, so teams run coverage from a script (`dotnet test --collect`, ReportGenerator; ours is `run-coverage.ps1`), which remains the better way
- Project Properties as a form and Visual Studio's Launch Profiles editor: Edit Project File covers the properties, and Open Launch Settings creates `launchSettings.json`, whose JSON schema helps with editing the profiles
